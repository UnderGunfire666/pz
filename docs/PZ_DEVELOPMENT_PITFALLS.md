# Project Zomboid 开发教训与本项目规避清单

这份文档整理了用户收集的《Project Zomboid》（PZ）开发层面问题，供 Afterlight 后续设计与代码审查时参考。它是一份风险清单，不是 PZ 缺陷的严格统计，也不代表每一项玩家报告都已查明根因。

## 版本背景与证据边界

截至 2026 年 10 月 1 日，材料记录的版本背景为 Build 42.20 于 2026 年 7 月进入 Stable，42.21 于 9 月作为 Unstable 发布。针对旧版渲染、光照或性能的讨论不能直接代表当前版本全部情况。PZ 开发者在 B42 对地图渲染与光照进行了重要调整，且仍持续推进优化、模组支持和技术债治理。

阅读和使用本清单时区分以下证据：

- 官方开发日志和版本说明适合确认开发者公开说明过的架构取舍、计划和已实现变化。
- 官方论坛中的可复现报告能证明某些版本、场景下出现过问题，但不能自动外推为所有版本都存在。
- 玩家帖子和评论能提示用户体验反复遇到的风险，不是故障率统计，也不能单独证明代码根因。
- 视频分析若无可核验逐字稿或独立数据，不把作者判断写成技术事实。
- “像素风/等距画面不好看”等审美意见与性能、正确性问题分开讨论。

材料引用的主要来源包括 PZ 官方 [42 Techdoid](https://projectzomboid.com/blog/news/2022/02/42-techdoid/)、[B42 技术升级日志](https://projectzomboid.com/blog/news/2024/01/hmm-upgradez/)、[B42.20 功能说明](https://projectzomboid.com/blog/features-overview-build-42-20/)、[B42 Unstable 说明](https://projectzomboid.com/blog/news/2024/12/build-42-unstable/)、[B42 后续计划](https://projectzomboid.com/blog/news/2026/07/next-steps-2/)及各项 Bug 报告。版本号和发布日期是该材料记录的背景；引用来源时仍应根据问题需要核对原文和适用版本。

## 主要技术债风险

### 1. 工作长期堆在每帧路径中

镜头缩放、建筑密集区域、大量角色、光照或 UI 更新，都可能让每帧工作失控。旧渲染管线的独特 tile/shader 和等距绘制次序曾带来 CPU/GPU 成本；B42 的分块缓存缓解了部分问题，也引入缓存显存成本，官方仍计划继续优化。

本项目的规避要求：

- 地图渲染按 chunk 管理；模拟、声音、导航和 AI 各自明确活跃范围与更新频率。
- 静态建筑、地形和装饰尽量复用或缓存；只有变化对象进入高频更新路径。
- 用“小而密”的场景压测地块、建筑、物品、僵尸、NPC 和光源同时出现的情况。
- 记录 CPU/GPU 帧时间、脚本阶段耗时、draw call、活跃实体数和内存；仅看平均 FPS 不足以定位卡顿。
- 避免所有对象始终激活，也不要把渲染分块误认为全图模拟和导航已经卸载。

### 2. 玩法逻辑依赖渲染状态

若用贴图亮暗表示 FOV、用渲染隐藏代表 AI 看不见，或把光照缓存与遮挡判定混在一起，渲染优化就可能改变玩法，显示和模拟也会互相矛盾。

本项目应保持一个权威的可见性结果，供玩家感知、敌人/NPC 感知、场景隐藏和迷雾显示共同使用。模拟判定包括距离、朝向、墙体 LOS、楼层和目标状态；画面负责 FOV、遮罩、淡出与光照表现。攻击命中也必须由玩法状态决定，不能由动画或屏幕像素推断。对网格地图尤其要检查格中心采样与格内连续视线之间的偏差。

### 3. 库存和长时间使用后的性能退化

大量物品、容器、右键菜单和 tooltip 是容易晚期出现的性能热点。玩家报告只能提示症状；不能仅凭帖子断言存在内存泄漏或特定多线程根因。

本项目应让 UI 只生成可见项目；缓存物品定义、图标和可复用排序/搜索数据；避免打开 tooltip 或转移一件物品时重扫附近所有容器。静态物品定义与运行时实例分离，常见物品可堆叠。压力测试要持续开关 UI、搜索、转移大量物品、存档读档，并观察内存和帧时间是否增长。

### 4. 单机状态模型若散落会抬高联机和调试成本

PZ 多人问题不能简单归因于某一个旧引擎或某一层；权威状态、网络同步、客户端呈现、服务器负载等都可能相关。单机项目无需提前引入网络架构，但应防止业务规则散落在 UI 与节点回调中。

本项目应由明确系统持有玩家、NPC 和世界状态；UI 读取状态并发送明确动作命令，如移动物品、开门、造成伤害。世界时间由统一时钟推进，事件记录时间或模拟步。表现与结果判定分离，保留状态变更原因日志。

### 5. 网格导航与动态障碍组合后的边界问题

门窗、家具、可破坏墙体、窄通道和楼梯一旦影响寻路、视线和交互，边界组合会迅速增加。个别 PZ 复现不能证明所有版本路径系统都不可靠，但值得把动态地图状态视为高风险接口。

本项目应区分可通行、可翻越、可破坏、可开关和需要绕行的属性。障碍变化时明确失效受影响区域的导航与可见性缓存。路径失败要能重试、换目标或放弃，并记录原因。自动化覆盖窄门、窗户、围栏、楼梯、多出口房间和动态障碍。知道目标位置不等于能穿障碍到达目标。

### 6. 美术方向和渲染架构彼此锁死

等距 tile、2D 精灵、3D 模型和混合渲染都有各自成本。风格简洁不等于技术落后；风险在于大量内容已经制作后，才发现楼层排序、遮挡、FOV 或光源需要推翻。

在扩充资产前，应确定角色、墙体、楼层、室内外和光源各自的表现边界。先做包含街道、建筑、室内、窗门、楼上楼下、遮挡与夜间光源的垂直切片。将屏幕内可见实体、透明层、光源和阴影预算纳入美术规范。

### 7. 视觉、光照、声音和玩法范围规则不一致

声音传播若不能解释僵尸或 NPC 的反应，会损害玩家对规则的信任。开枪后无反应、隔墙精准追踪等体验往往来自范围、遮挡、楼层和记忆规则不一致。

声音应作为数据化世界事件，至少携带声源位置、类别、强度和发出时间。由传播规则计算距离衰减、墙门窗与楼层影响，再由听者状态决定如何更新线索和记忆。NPC/僵尸接收模糊声源，不应默认获得玩家精确坐标。开发期提供声音半径、衰减与障碍惩罚调试显示。

### 8. UI 与模拟系统耦合

选项和物品增加后，界面容易拥挤、重复刷新或展示不同步。官方曾公开改造复杂菜单和配方 UI；这应作为长期维护的提醒，而非断言 PZ 所有 UI 都有同一缺陷。

本项目 UI 只读取模型并发送明确命令，不持有第二份背包、玩家状态或世界状态。根据数据变更刷新 UI，不逐帧重算全部项目。关键动作说明耗时、风险、目标及失败原因，并在常见分辨率下检查布局、字体、缩放和键鼠操作。

### 9. 扩展只能覆盖核心文件

若模组或内容扩展必须替换核心脚本，版本更新就会造成长期兼容负担。MVP 不需要完整模组 SDK，但应让内容资源、可插拔行为和核心逻辑保持边界。

稳定扩展接口应有版本、弃用与迁移说明。资源加载失败应指出资源路径、字段和预期版本，而不是只报告通用错误。

### 10. 存档与模组在大版本升级中断裂

长期沙盒中，玩家世界本身具有价值。PZ 曾有大版本存档和模组不兼容的官方提示；单机项目同样需要把升级失败视为用户数据风险。

本项目的存档要有明确 schema 版本和可重复迁移；迁移前备份，失败时保留原档。迁移测试至少涵盖玩家、容器、地图、实体和世界时间。区分格式迁移与平衡调整，避免两者绑成无法回滚的大改动。

### 11. 超长开发周期让功能缺失变成体验问题

PZ 的长周期开发引发过玩家对等待、路线图落差、改动规模和更新间隔的不满；这类反馈不是所有玩家的共同评价，也不能仅凭评论推导开发质量。

本项目应让每个系统先有可玩、可验收的窄版本。使用可在数周内验收的垂直目标，而非只以“完成 NPC 系统”这类大主题追踪进度。NPC 愿景不能长期推迟移动、视野、声音和搜刮组成的基础生存循环。

### 12. 系统复杂但长期目标薄弱

深度和自由度是优势；部分玩家也会在初期危险过去后感到活动重复、长期目标不足。这是玩家体验反馈，不是对所有玩家的客观结论。

本项目的 NPC 必须改变玩家选择，而不只是在场景里移动。小规模行为也可以留下搜刮痕迹、打开门引来声音、避开玩家或因威胁改变计划。先验证少量可解释行为是否形成选择，再增加人格字段和模拟复杂度。

### 13. 隐性生存规则使失败显得不公平

严厉规则若无法理解，玩家容易把失败归因于随机或错误。伤害、疲劳、负重、保暖和感染尤其需要可追溯状态变化。

本项目应区分普通伤口感染与僵尸病毒感染；提示流血、疲劳、口渴、负重和动作中断等风险。隐藏信息可以存在，但关键后果需要合理线索，事后日志能说明角色何时、为何发生状态变化。

### 14. 新旧实现混杂，修复范围越来越难判断

长期代码库必须持续治理边界。具体玩家帖子难以证明某模块采用了某种遗留代码，但公开开发计划常会提到技术债、流程与支持工具的改进。

每个系统有一个状态所有者和清楚接口；玩家控制器不同时承载生存、声音、战斗和 UI 规则。规则逻辑与可调静态数据分层。修复从最小复现开始并添加回归场景。重构与大型新功能分批进行。

### 15. 地图规模增长推高资产、验证和加载成本

独特建筑、tile、家具、光照与容器组合会增加制作、验证和加载成本。小区域若有密度和环境叙事，同样能形成丰富探索。

本项目应优先打磨 Orangeville 的密度和差异，不预先扩大整座城市。地图编辑器除摆放内容外，还应验证地块、房间、出入口、导航、容器和僵尸压力数据。扩大地图前测量导航、内存、加载与运行帧时间。

### 16. 组合场景缺少回归覆盖

游戏的模组、多人、楼层、车辆、光照、障碍和存档组合空间很大。公开 Bug 讨论无法证明开发团队的内部覆盖率，但反复出现的复杂边界案例说明回归场景很重要。

优先维护自动化测试：移动与连续视线、墙体遮挡、声音传播、门窗/楼梯路径、动态障碍、容器转移与负重、存档迁移、NPC 目标取消、暂停与快进。迁移失败时验证原档仍可用。每次修复至少留下可重复验证的用例。

## 本项目长期采用的八条检查项

进行相关设计或代码审查时，优先核对以下事项：

1. 模拟和渲染分离。FOV、光照、隐身、命中和 AI 感知不通过画面效果互相推断。
2. 地图数据、实体模拟和渲染各自定义区域/chunk 的所有权、活跃范围和更新频率。
3. 大容器、邻近容器、右键菜单和 tooltip 有明确性能预算。
4. 动态障碍变化能让对应寻路和可见性缓存失效。
5. 声音可作为世界事件调试，能解释 NPC/僵尸反应方向和目标记忆。
6. 存档早期版本化，迁移有回滚保护和真实旧档测试。
7. 每个系统先服务一个可玩的生存循环，不让工具或内容规模长期挤压基础玩法。
8. 用代表性的拥挤场景建立性能基线；不等地图扩大后才测。

## 面向 Afterlight 的审查约定

- 本文是设计审查辅助，不要求复制 PZ 的系统，也不要求为了未来联机提前引入网络层。
- 对当前项目中的视野与迷雾，重点检查连续世界坐标的 LOS、格子探索记录和高分辨率画面遮罩是否使用一致规则；网格仍可作为地图、导航和持久化数据结构。
- 对库存、僵尸/NPC、地图编辑器和渲染分块，先沿用现有状态所有者与更新节奏，再根据剖析数据优化；避免为抽象而抽象。
- 新实现若与本文冲突，应说明具体取舍、性能证据与回归覆盖；本文不是禁止合理设计变化的硬性规范。
